# ПУЛЬС — руководство по контрактам API

> **Статус:** протокольная спецификация для реализации и контрактного тестирования, 11.11.2026. Не означает существования обработчиков, работающих серверов или проведённого браузерного тестирования.  
> **Версия публичного API:** `v1` (`/api/v1`). **Формат:** OpenAPI `3.1.0` и JSON Schema 2020-12 в `components.schemas`.  
> **Источники решений:** `01` — конкурс и защита; `02` — продукт; `03` — ФТ-01–ФТ-77 и НФТ-01–НФТ-23; `04` — 31 сценарий и ТД-01–ТД-20; `05` — архитектура и HTTP-инварианты; `06` — предметная модель; `07` — UX/состояния экранов. Приоритет предметных уточнений — как в 05 §1. Иные документы не менялись.

## 2. Доверенные границы

```text
Браузер студента —HTTPS, cookie→ собственный Next.js /api/v1
                                             ├→ PostgreSQL (локальные P: сессия, заявка, обращение, сообщение, прочтение)
                                             ├→ серверные проекции V (сводка, уведомления, календарь)
                                             ├→ адаптеры R → приватные фикстуры test API (вымышленные учебные данные)
                                             ├→ закрытый worker (outbox/опрос внешних состояний)
                                             └→ серверный ИИ-провайдер/демо-замена
```

Браузер обращается **только к собственному Student API**. Второй YAML не предназначен для публичного маршрутизатора, мобильного браузера, CORS для внешних origin или выдачи тестовых ключей клиенту. Внутренний серверный provider может быть in-process; тогда спецификация внешних HTTP-операций остаётся контрактом транспортного теста и семантики порта, а не требованием развернуть дополнительный публичный сервис.

Личность студента определяется по доверенной серверной сессии и её карте `student_external_identity`. При запросе внешних сведений сервер проверяет `(account, externalStudentId, sourceCode, periodId, offeringId, membership, official subgroup, audience)` перед чтением и валидирует **каждый** объект после ответа. Внешний тестовый сервис не заменяет авторизацию Student API. Чужой/несуществующий ID в публичном детальном GET/POST возвращает одинаковый безопасный `404`. Нельзя раздавать R-схемы напрямую в React: внешние `sourceCode`, `requestedScope`, `ExternalRef`, `externalStudentId`, внутренние URI, ключи и исходные payload не входят в публичный сериализуемый allowlist.

## 3. Аутентификация и безопасность команд

- Собственный API — same-origin HTTPS; серверная cookie `__Host-puls_session`, `Path=/; Secure; HttpOnly; SameSite=Lax`, без `Domain`. Логин создаёт новый случайный токен сессии; в БД хранится только дайджест. Пароль Argon2id. Состояние сессии — 12 часов от последней активности и максимум 7 суток от выпуска, как в 05 §4; API-контракт не создаёт иную политику.
- `POST /auth/login`, `/auth/logout` и **все** прочие изменяющие публичные методы требуют точный заголовок `Origin` собственного приложения. Пустой/посторонний `Origin` → `403 CSRF_ORIGIN_INVALID`; `Sec-Fetch-Site` — дополнительный контроль. Внешние машинные вызовы идут по отдельной внутренней аутентификации `X-Internal-Token`, не по браузерной cookie.
- Каждый приватный JSON, поток, PDF/XLSX/ICS и ответ помощника: `Cache-Control: private, no-store`, `Vary: Cookie` при необходимости. Секреты и сырой вопрос ИИ не записываются в открытые логи. Нет универсального `/students/{id}` в публичной зоне.
- `POST /requests`, `/appeals`, `/appeals/{id}/messages` требуют `Idempotency-Key` — UUID v4 одного намерения. Одна и та же комбинация `(account, scope/parent, key, canonical payload)` возвращает **тот же объект**; тот же ключ с другим payload → `409 IDEMPOTENCY_CONFLICT`. Срок технической дедупликации — 24 часа после commit. Не создавать второй объект из-за сетевого тайм-аута.
- `POST /operations/resolve` принимает `operationScope` + прежний ключ и только проверяет состояние `COMMITTED|PENDING|NOT_FOUND|EXPIRED`; не отправляет повторную заявку. Если сам resolver недоступен, интерфейс сохраняет состояние «Не удалось установить результат отправки» и не повторяет создание автоматически. `NOT_FOUND` после истечения retention **не** доказывает несуществование исторической заявки.
- Уведомления меняют **только персональные отметки прочтения**. `POST /notifications/read-all` действует на все доступные аккаунту события **пяти категорий**, независимо от фильтров и страниц; тело без `category/cursor/limit`. Транзакция атомарна по проверенному набору. При неполной доступности категорий ответ `200` с `completeness: PARTIAL` и `unavailableCategories`, а не ложное «Всё прочитано».
- Учебные сущности, оценки, подгруппы, посещаемость, работы и календарь — **только чтение**. Нет POST на сдачу учебных файлов, выставление отметок, переключение подгруппы, создание личного события, редактирование чужих записей и изменяющих вызовов ИИ.

## 4. Стиль путей, DTO и наблюдаемые состояния

`/api/v1` — базовый путь публичного сервера, версии с несовместимыми контрактами получают `/api/v2`. Имена путей — `kebab-case`, публичные поля JSON — `camelCase`, `operationId` — уникальный глагол + предметный объект (`getOfferingDetail`, `createRequest`). Внешние URI начинаются от **приватного** `/mock/v1`, а внутренние DTO идентифицируются `(sourceCode, objectKind, externalId)`; это не сквозные публичные URL.

Публичный успех JSON: `{ "data": ..., "meta": { "requestId": "...", ... } }`. Публичная ошибка JSON: `{ "error": { "code": "...", "message": "...", "details": [...] }, "meta": { "requestId": "..." } }`. У сообщения ошибки — русский текст, `details` лишь с безопасными именами неверных полей, без чужих ID, приватных URI, SQL, raw stack traces или токенов. Публичная `meta` допускает только `requestId`, `sourceStatus`, `completeness`, `completenessByDataset`, `completenessByCategory`, `fetchedAt`, `sourceUpdatedAt`, `partialErrors` безопасных категорий — не сырой объект `ExternalRead`.

Внешнее чтение: `sourceCode`, `requestedScope`, `availability: OK|PARTIAL|NO_DATA|NOT_APPLICABLE|ERROR`, `isComplete: true|false|null`, `fetchedAt`, `sourceUpdatedAt?`, `sourceRevision?`, `items[]`, `nextCursor?`. `NO_DATA` допускается **только** для пустого подтверждённо полного набора; `NOT_APPLICABLE` — подтверждённое отсутствие конкретного вида деятельности; `ERROR` — не пустой успех. В публичном представлении также различаются `UNKNOWN`, `PENDING`, `KNOWN_ZERO`, `SOURCE_ERROR`, `FORBIDDEN`, `EMPTY_CONFIRMED`. Ноль — известное значение, не замена пустоты. Неполная attendance не даёт достоверных процентов.

Дата без времени: `{precision:"DATE_ONLY",on:"YYYY-MM-DD"}`. Дата со временем: `{precision:"DATE_TIME",at:"2026-11-11T10:00:00+06:00",timeZone:"Asia/Omsk"}`. Факт выдачи, срок, сдача, проверка, оценка и `fetchedAt` **не взаимозаменяемы**. Балльные значения передаются точной **десятичной строкой**, а не float. Дисциплина идентифицируется `offeringId + periodId`; самостоятельная курсовая — `unitId + periodId`, **без** поддельного offering. План пары, факт проведения и персональная посещаемость — разные DTO. Выданная работа не равна невыполненной; материал «Конспект.pdf» не равен заданию «Подготовить конспект».

### 4.1. Списки и поиск

Для длинных списков `limit` в диапазоне `1–100`, начальная порция — 20 (переписка: последние 30). Ответ содержит `items`, `nextCursor`, `isComplete`, `dataState`. Курсор непрозрачен, подписан/связан с аккаунтом, scope и фильтрами; замена пользователя, filter hash или source revision → безопасный `409 SOURCE_REVISION_CHANGED`/ошибка курсора. При ошибке следующей порции ранее полученное не обнулять. Если `nextCursor=null`, это окончание данной подтверждённой выборки, а не заявление о полноте других источников. Для списка могут быть дополнительные параметры `periodId`, `offeringId`, `category`, `unreadOnly` только там, где они явно описаны в YAML.

`GET /academic/search?q=...&limit=10` — **серверный** поиск по всем разрешённым семестрам и работам, а не по первым 20 элементам текущей страницы. Результат содержит тип, название, контекст периода, непрозрачную разрешённую ссылку и `COMPLETE|PARTIAL`. У разных семестров одинаковые имена не сливаются. UX 07 обеспечивает переход из поля главной к доступному результату без дополнительной страницы поиска. Недоступный источник не позволяет объявить «совпадений нет» как подтверждённый факт.

### 4.2. Ошибки HTTP (на конкретных операциях применимы только перечисленные в YAML)

| Код | Назначение | Типичный безопасный код ошибки |
|---|---|---|
| `400` | Синтаксически повреждённый запрос | `BAD_REQUEST` |
| `401` | Нет сессии, неверные учётные данные, сессия истекла | `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `SESSION_EXPIRED` |
| `403` | Явно запрещённый тип действия или неверный Origin | `ACCESS_FORBIDDEN`, `CSRF_ORIGIN_INVALID` |
| `404` | Неизвестная или чужая защищённая запись (одинаковый ответ) | `NOT_FOUND` |
| `409` | Конфликт идемпотентности, ревизии страницы, версии формы, выбранного календаря | `IDEMPOTENCY_CONFLICT`, `SOURCE_REVISION_CHANGED`, `FORM_SCHEMA_CHANGED`, `CALENDAR_SELECTION_CHANGED` |
| `413` | Превышен лимит команды, диапазона или количества событий | `PAYLOAD_TOO_LARGE` |
| `415` | Для POST с JSON-body передан иной `Content-Type` (требуется `application/json`, допускается `charset=utf-8`); операция не выполняется | `UNSUPPORTED_MEDIA_TYPE` |
| `416` | Клиент запросил неподдерживаемый частичный диапазон демонстрационного файла | `RANGE_NOT_SUPPORTED` |
| `422` | Формальные ошибки полей/фильтров либо полный пустой экспорт | `VALIDATION_ERROR`, `CALENDAR_SELECTION_EMPTY` |
| `429` | Лимит логина, команд или помощника | `RATE_LIMITED`, заголовок `Retry-After` при наличии |
| `502` | Невалидный ответ источника | `EXTERNAL_INVALID_RESPONSE` |
| `503` | Источник или полный экспорт недоступен | `EXTERNAL_UNAVAILABLE`, `SOURCE_INCOMPLETE` |
| `504` | Истёк тайм-аут | `EXTERNAL_TIMEOUT` |

Заявка после локального commit имеет `localState: STORED`, `businessStatus: null`, `externalState: PENDING`; **это не «Отправлена»**. Предметные состояния `SUBMITTED`, `IN_PROGRESS`, `READY`, `REJECTED` принимаются только от подтверждённого mock source с устойчивым `operationId`, `externalOperationId` и ревизией. Технические `UNKNOWN`, `RETRYABLE_ERROR` и `PERMANENT_TECHNICAL_ERROR` не добавляются в список административных статусов. Обращение имеет категории `QUESTION|PROBLEM|OTHER`, предметное состояние `OPEN`, первая реплика создаётся атомарно с обращением, затем сообщение отправляется отдельной идемпотентной командой. Ответная сторона — «Деканат (демо-ответ)», вложений нет.

## 5. Точный контракт демонстрационных форм

**Единый каталог v1**, используемый одновременно в OpenAPI, Zod, UI, seed и локальной истории. Не возвращать прежние поля `purposeComment`/`statementText`.

| Тип и название | Только допустимые поля `submittedData` |
|---|---|
| `DEMO_CERTIFICATE` — «Справка об обучении (демо)» | `copies`: целое обязательное 1–5 (интерфейс предлагает 1); `presentationPlace?`: ≤160 символов; `comment?`: ≤500 символов |
| `DEMO_APPLICATION` — «Общее заявление (демо)» | `subject`: обязательные 3–120 символов; `statementBody`: обязательные 10–3000 символов; `comment?`: ≤500 символов |

Каталог `RequestType` возвращает строго соответствующие друг другу `requestTypeCode`, `kind`, название и три описания полей, включая обязательность, тип и ограничения; несогласованная пара и пустой `fields` не являются допустимым успешным ответом. `formSchemaVersion: v1`, лишние поля в командах отклоняются (`additionalProperties: false`). Сервер проверяет связь типа и payload, нормализует крайние пробелы/переносы по согласованной реализации и хранит снимок версии. При устаревшей версии — `409 FORM_SCHEMA_CHANGED` до commit. Не добавлять реальные паспортные реквизиты, вложения, сроки получения и университетские правила.

## 6. Календарь, экспорт и файлы

Одна `CalendarSelection` передаёт **одинаковые** `from`, `to`, `eventKinds` в три операции:

1. `GET /calendar?from=...&to=...&eventKinds=UNIVERSITY,ACADEMIC` — показ; при `PARTIAL` допускаются только подтверждённые элементы с предупреждением.
2. `GET /calendar/export-preview?...` — разрешён только полный, непустой набор в пределах 366 дней и лимита 5000; возвращает `count`, `selectionToken`, `expiresAt` (5 минут) и фильтры. При `PARTIAL` — `503 SOURCE_INCOMPLETE`, при полном нуле — `422 CALENDAR_SELECTION_EMPTY`.
3. `GET /calendar/export?format=ics|pdf|xlsx&...&selectionToken=...` — заново проверяет сессию, scope, полные данные, версии, digest канонического списка и токен. Изменение/истечение — `409 CALENDAR_SELECTION_CHANGED` **без файла**. Один неизменяемый экспортный DTO поступает в выбранный сериализатор. Отдельные запросы трёх форматов гарантируют одинаковую выборку лишь пока она не изменилась, иначе сервер отклонит несовпадение.

`eventKinds=UNIVERSITY` включает университетские события, `ACADEMIC` — подтверждённые сроки и аттестации. Это **видимые категории фильтра**, не дополнительные коллекции. `selectionToken` не является доступом к чужим событиям. ICS: `text/calendar; charset=utf-8`, RFC 5545; PDF: `application/pdf`; XLSX: `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`. Все ответы — `Content-Disposition: attachment`, корректное безопасное имя и no-store. `DATE_ONLY` экспортируется в ICS как `VALUE=DATE` (календарные клиенты могут показать «весь день»), без искусственных 23:59. XLSX трактует потенциальные `= + - @`, табуляции и переносы как **текст**, не формулу. Никаких статических файлов-имитаций экспорта.

`GET /materials/{id}` даёт проверенные метаданные или разрешённую HTTPS-ссылку для `LINK`; `GET` и `HEAD /materials/{id}/download` повторно проверяют права на `FILE` и возвращают байты из доверенного хранилища/серверного fixture API. Клиент не задаёт адрес скачивания. Не принимать произвольный URL/IP/файловый путь для серверного запроса, не раскрывать presigned credentials, фильтровать MIME и размер. Академические материалы только для чтения, нет upload.

## 7. Тестовые источники и воспроизводимость

`Контракты_внешних_систем.yaml` описывает fixture-backed ответы по scope, а не 1:1 копию физической схемы PostgreSQL. Серверные read-адаптеры `AcademicContextPort`, `SchedulePort`, `AcademicWorkPort`, `ResultsPort`, `MaterialsPort`, `AnnouncementsPort`, `CalendarPort` нормализуют ответы и отклоняют неподтверждённые связи. Командные порты `RequestCommandPort` и `AppealCommandPort` сверяют удалённый `operationId` после неизвестного исхода, повторяют **только с тем же ID** и никогда не генерируют ложные статусы. `listReplies` возвращает стабильный `externalMessageId` с дедупликацией; fixture не становится кабинетом реального сотрудника. Внутренние ключи и наборы режимов фикстур выбирает сервер, не query-параметр публичного Student API.

Контрольные наборы из 04, ТД-01–ТД-20: два изолированных аккаунта; разные официальные подгруппы по дисциплинам; перенос/отмена занятий; балльная дисциплина+экзамен, безбалльная дисциплина+конспект+курсовая+зачёт; одинаковая дисциплина в двух периодах; план без проведения, подтверждённые присутствие и отсутствие; выданная работа с неизвестным выполнением; оценённая и сданная работы; курсовая с этапами и без; материал «Конспект.pdf» и отдельное задание; подтверждённый нулевой балл; разные аудитории событий; событие изменения одного срока во всех проекциях и форматах; timeout после фактического ACK; дублирующийся reply; `PARTIAL`, `NO_DATA`, `ERROR`, неправильная ревизия и чужие объекты. Не смешивать фикстуры разных source revisions в одном якобы полном snapshot.

## 8. Валидация контрактов и использование в Codex

1. Зафиксировать оба YAML в репозитории без переименований, **сначала прочитать** 03–07 и этот README, не подменять внешние read-model таблицами БД. Публичные DTO и обработчики генерировать/проверять против `Контракт_студенческого_API.yaml`, адаптеры и фикстуры — против `Контракты_внешних_систем.yaml`.
2. Локально проверить YAML parse, OpenAPI 3.1, refs, уникальные `operationId`, JSON Schema и примеры. Для полной стандартной проверки, после установки совместимого инструмента, выполнить `python -m pip install openapi-spec-validator openapi-schema-validator` и проверять оба файла средствами `openapi_spec_validator`; отдельно выполнить `jsonschema.Draft202012Validator.check_schema` для каждого `components.schemas` и тестовую проверку опубликованных примеров. Без фактического запуска полного валидатора **не объявлять** прохождение полной OAS-валидации.
Пример независимого запуска полноценного OAS-валидатора **после установки зависимости** (не входит в архив):

```bash
python -m pip install openapi-spec-validator
python - <<'PYVALIDATE'
from pathlib import Path
import yaml
from openapi_spec_validator import validate_spec
for path in Path('документация/API').glob('*.yaml'):
    validate_spec(yaml.safe_load(path.read_text(encoding='utf-8')))
    print('OpenAPI OK:', path)
PYVALIDATE
```

В текущем подготовленном комплекте проведена структурная проверка моделью OpenAPI 3.1 FastAPI, проверка схем JSON Schema Draft 2020-12, внутренних ссылок, имён операций, параметров, примеров и отрицательных кейсов. Ввиду отсутствия сетевого доступа отдельный пакет `openapi-spec-validator` не удалось установить; этот дополнительный независимый тест следует выполнить в среде реализации. Проверка выше не заменяет проверку работающих серверов.

3. После создания серверных Zod DTO написать контрактные тесты: успешные ответы/ошибки/заголовки, неизвестные поля форм, старую версию, истёкшую cookie, чужой объект, подменённую подгруппу, курсор другого аккаунта, частичность источника, `KNOWN_ZERO`, `NOT_APPLICABLE`, `SOURCE_REVISION_CHANGED`, `Idempotency-Key` повтор и конфликт, `MUTATION_UNCERTAIN`, повтор внешнего ACK и дублирующийся reply.
4. Реализовать `buildCalendarSelection()` как единый проверенный конвейер для экрана, preview и трёх форматов. Тестировать `DATE_ONLY`, новую source revision, пустой набор, `PARTIAL`, истечение token, одинаковые IDs/точность в ICS/PDF/XLSX и формульную инъекцию в XLSX. Для бинарных ответов проверять реальные MIME, заголовки, парсинг формата и отсутствие файла при ошибке.
5. Прогнать СЦ-01–СЦ-24 (включая буквенные и дробные ID), ТД-01–ТД-20, тесты двух аккаунтов и UI 360 px; фактическое прохождение возможно **только** после создания приложения. Каждый `x-trace-scenarios` — подсказка для отбора фикстур, не доказательство уже выполненного теста.

Совместимость при изменениях: *дополнительное необязательное* публичное поле обычно обратно совместимо; удаление/переименование обязательного поля, изменение enum, маршрута, security, значения статуса или точности времени требует оценки и обычно новой версии `/api/v2`. Параметры форма-v1 не менять молча: новая схема — новая `formSchemaVersion`, старые заявки продолжают читаться по исходному снимку. Ревизии тестовых источников и `sourceUpdatedAt` не являются версией публичного протокола. Перед коммитом сравнивать оба YAML и обновлять одновременно DTO, fixture schema, контрактные тесты и вызывающие экраны, если изменено их общее значение.

## 9. Границы подтверждения

Документы специфицируют протокол **до реализации**. Структурная YAML/JSON Schema-проверка и примеры подтверждают корректность артефактов в своей области, но **не** безопасность реального сервера, работу mock-адаптеров, соответствие WCAG или успешные экспорты. Полные архитектурные/сквозные испытания проводятся после написания кода и развёртывания. В составе поставки нет тестовых секретов, реальных персональных данных и дополнительного API для административных ролей.
