# Развёртывание ПУЛЬС

Конфигурация в корне проекта: `Dockerfile`, `compose.yaml`, `deploy/Caddyfile`. Она описывает PostgreSQL 17, отдельный запуск миграций Prisma, Next.js, worker доставки и HTTPS через Caddy. На дату подготовки автоматический CD и публичный сервер не подключены; эти команды не являются отчётом о выполненном деплое.

## Первый запуск на сервере

1. Установите Docker Engine с Compose plugin, подключите домен к серверу и откройте 80/443. Сервер должен быть доступен из России без VPN.
2. Создайте **вне Git** защищённый файл окружения. Обязательные имена перечислены в `.env.example`; для Compose заполните `POSTGRES_PASSWORD`, `PULS_WEB_PASSWORD`, `PULS_HOST`, `APP_ORIGIN`, `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `AUTH_RATE_LIMIT_HMAC_KEY`, `TRUSTED_PROXY_KEY`. `APP_ORIGIN` — точный HTTPS origin домена. URL БД используют host `db`: runtime — роль `puls_web`, миграции — `puls_owner`. Пароли должны быть разными. Не копируйте локальные `.env.local` и демонстрационные пароли на публичный сервер.
3. Проверьте состав релиза и конфигурацию, затем запустите:

   ```sh
   docker compose --env-file /secure/path/puls.env config --quiet
   docker compose --env-file /secure/path/puls.env up --build -d
   docker compose --env-file /secure/path/puls.env ps
   ```

4. На **новой** базе создайте два вымышленных демонстрационных аккаунта через `docker compose --env-file /secure/path/puls.env run --rm -it migrate pnpm db:seed`. Seed запросит два разных пароля скрытым вводом. Он не должен запускаться при каждом релизе. Перед показом жюри проверьте вход обоих студентов, чтение их собственных данных и работу worker. Не публикуйте эти пароли в Git, CI или документации.
5. Проверьте HTTPS и сертификат Caddy снаружи. Проверка только `localhost` не доказывает доступность публичного сервера.

Обычное обновление: сначала создать резервную копию, затем развернуть проверенный Git SHA через `docker compose ... up --build -d`. `migrate` применяет миграции до запуска web и worker. Текущая схема миграций должна быть совместима с предыдущим образом; откат к предыдущему SHA допустим только при подтверждённой совместимости. `docker compose down -v` удаляет данные и для обновления не применяется.

## Резервная копия и восстановление

`deploy/backup.sh /secure/path/puls.env /secure/backups` создаёт `pg_dump` в custom format, проверяет оглавление, формирует SHA-256 и не оставляет частичный файл при ошибке. Проводите ежедневный запуск через системный планировщик, контролируйте завершение и храните зашифрованную копию вне VPS с ограниченным доступом. Локальная копия на том же сервере не защищает от потери VPS.

Проверка восстановления выполняется в **отдельной изолированной среде**, никогда в работающей `puls`:

1. Сверьте SHA-256 и наличие шифрованной внешней копии. Расшифруйте её только во временной защищённой директории.
2. Поднимите отдельный PostgreSQL 17 и создайте пустую БД `puls_restore_check`.
3. Выполните `pg_restore --exit-on-error --no-owner --no-acl --dbname puls_restore_check <копия.dump>` с ролью владельца этой тестовой БД.
4. Сверьте число аккаунтов, собственных заявок, сообщений и уведомлений с контрольными значениями до копирования; проверьте внешние ключи, вход двух тестовых аккаунтов и изоляцию данных. Не используйте реальные пароли в отчёте.
5. Удалите временную среду и расшифрованный файл по принятой политике хранения.

Перед восстановлением боевой БД отдельно остановите web и worker, сохраните аварийную копию текущего состояния и составьте план смены DNS/тома. Эта процедура требует ручного решения оператора: автоматическое восстановление поверх работающей БД не настроено.

## Внешний ИИ

По умолчанию включён явно обозначенный `DEMO_MOCK`. Для GigaChat нужен серверный ключ, подходящий `GIGACHAT_SCOPE` и доверенный TLS сертификат провайдера в Node.js. Ключ и сертификаты не помещаются в Git или в публичный образ. Проверка реального GigaChat и настройка доверия на целевом сервере выполняются отдельно.
